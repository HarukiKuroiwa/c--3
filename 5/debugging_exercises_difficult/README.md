# デバッグ演習 (difficult)

easy では「症状の近くに原因がある」バグを扱いました。difficult のバグは、次のような理由で見つけにくくなっています。

- **特定の入力でだけ失敗する**：一部のテストは正しく動くので、「どの条件で壊れるか」を絞り込む必要がある
- **症状と原因の場所が離れている**：プログラムが落ちた場所や、おかしな値が見えた場所に、原因があるとは限らない
- **1か所直しても、まだ残る**：直したつもりでも、別の条件で再び失敗する

| 問題 | テーマ | 症状 |
|---|---|---|
| `set1_multidimensional_arrays` | 2次元配列と添字計算 | 3×3 は正しいが、2×4・4×2 の回転結果が崩れる |
| `set2_linked_lists` | 連結リストとメモリ解放 | 最初のテストは正しいが、2つ目以降でおかしくなる |
| `set3_multithreading` | 排他制御 | mutex を使っているのに座席を売りすぎる |
| `set4_file_io` | ファイル入出力と文字列処理 | 一部のファイルで行数・単語数が `wc` と合わない |
| `set5_binary_search_tree` | 二分探索木と再帰 | 一部の削除で木が壊れる |

## 進め方（各問題のフォルダで）

```bash
cd set1_multidimensional_arrays
cat README.md     # 仕様・期待される出力・症状を読む
make run          # 症状を自分の目で確認する
                  # → 「どのテストは正しく、どのテストがおかしいか」を整理してから原因を探す
make check        # 判定。PASS なら完了
```

## make check が見ていること

1. **コンパイル**：警告が出ていれば表示します
2. **出力の比較**：実行結果が `expected.txt` と一致するか（set3 は5回実行して5回とも）
3. **サニタイザ**：出力が正しく見えても、メモリの範囲外アクセス・解放済みメモリへのアクセス・スレッドの競合などが残っていないか

3つすべてが OK になると **PASS** です。全問まとめて判定するには、このフォルダで `make check` を実行します。

## 注意

- 修正するのは `problem.c` だけです。`expected.txt`・`Makefile`・`tests/` は変更しないでください
- レポートには、各問題について次の3点を書いてください
  1. どの条件のときに失敗するか（失敗しないのはどんなときか）
  2. 原因は何か（どの行の、何が間違っていたか）
  3. なぜその修正で直るのか
- Mac では `gdb` の代わりに `lldb` を使います

## 提出のしかた

1. `REPORT.md` に学籍番号・氏名と、各問題の 1〜5 を書く（見出しは変えない）
2. このフォルダで次を実行する
   ```bash
   make submit ID=学籍番号
   ```
3. できた `submit_…_学籍番号.zip` を提出する

PASS していない問題があっても提出できます。その場合も、分かったところまでをレポートに書いてください。

## AIの使い方と作業記録

- AI に質問しながら進めてもかまいません。ただし、AI の答えを **自分で実行して確かめる** こと。
  使った場合は `REPORT.md` の「AIの利用」に、何を聞き、どこを自分で確かめたかを書いてください
- レポートの「5. 観察と調べ方」には、**自分の環境で実際に見た出力や値** を貼ってください。
  これが書けていない問題は満点になりません
- `make run` と `make check` を実行するたびに、時刻・結果・`problem.c` の変更点が `.worklog/` に自動で記録され、
  提出ファイルに含まれます。消したり書き換えたりしないでください
